Build your first Flow from a description

Describe the Thursday routine in one sentence, let Nexi draft the Flow, read the plan, fix the schedule and the Goal, test it without side effects, publish it and watch a real run park on your approval. About twenty-five minutes.

For: builderRequires: Project owner or editor to draft, edit and test; Project owner to publish and to decide the approvalLast verified against the application: 2026-09-18

Goal

An agent answers when you ask. A Flow works when it is time — every Thursday, when a file arrives, when someone presses Run. In this chapter you build the Flow from The example: plan the weekend — propose, keep improving until it fits the budget, let a person approve, then act. You will not draw anything; you describe it in one sentence and Nexi drafts the steps. Then you do what a builder always does with a draft: read the plan, correct the two things the machine guessed wrong, test it with nothing at stake, and publish.

Three ideas carry the chapter — the vocabulary is in Agents, Skills, Tools and Flows: Flow orchestrates. Goal directs. Evaluator judges.

  • a Goal is a measurable target with limits — budget_fit ≥ 0.9, at most 6 passes, at most 60 minutes;
  • the engine, never the model, decides whether the goal is met, and stops at the limits;
  • an approval is a step where the Flow waits for a person — in a test it is simulated, in a real run it waits.

Who can do this

RoleCanCannot
Project owner or editorDescribe and draft a Flow, edit every node and the Goal in Flow Studio, run “Test with data” on a draft.Publish, or start a real run of a published Flow (owner only). Bind an agent the Project does not have.
Project ownerPublish a version, start a real run, cancel a run, decide the approval the Flow parks on.Edit a published version — a published version is immutable; “Ask Nexi to modify” drafts the next one.
Any memberOpen the Flow, read every version, follow a run step by step, see who started it and how it ended.Change, test, publish or run.
The agent inside the FlowDo the work of its step and report metrics.Decide the loop is done, skip the approval, or start another Flow. The engine reads its metrics and decides.

Before you start

  • A Project you own or edit. The screenshots use Family weekends, a fresh Project; Weekend trips from the earlier chapters works just as well.
  • Nothing else. The drafted Flow uses the Project's general agent; you do not need the Trip planner for this chapter.

Steps

1. Open Flows

In the Project header press Flows.

You should see:

An empty page with one promise: Describe an automation in one sentence — Nexi drafts the steps, you review the plan, then test and publish. That is the whole method of this chapter, in order. Press New flow.

2. Say what the Flow should do

The dialog asks What should this flow do?

You should see:

One text box, three example sentences you can try later (a weekly supplier price report, a contract review, a Monday digest), and a quiet Start with an empty canvas for the day you want to draw by hand. Notice the shape of the examples: when it runs, who does what, what comes out, and who approves. A good sentence for a Flow has the same four parts.

Type the sentence and press Draft flow:

Every week on Thursday, plan the weekend for the family: propose two options and keep improving them until budget_fit >= 0.9, then I review the plan before it goes to the calendar.

You should see:

Four things in that sentence become four things in the Flow. Every week on Thursday → a schedule trigger. Keep improving … until → a loop with a Goal. budget_fit >= 0.9 → the Goal's success criterion, written as metric, comparison, number — write it that way and the drafter can read it. I review → an approval step for the Project owner. Two options and the calendar are for the agent to understand; nothing in the Flow's structure depends on them.

3. Read the plan before you open anything

A card appears while the draft is being saved.

You should see:

The plan is the checkpoint. Six numbered lines, one per step, in the words of what will happen — Starts: On schedule · Loops up to 10 times (≤ 60 min) until the goal is met: budget_fit ≥ 0.9 · Each iteration the agent works on the goal and reports metrics · The engine compares metrics with the criteria — agents never decide completion · A Project owner reviews the result (met, exhausted or stalled) before publishing · The run ends and every step stays in the audit trail. Then ✓ Valid and the reminder that nothing runs until the flow is published. Under This project the draft is already listed — On schedule · 4 steps · v1 · Goal loop · Draft. If the plan is wrong, this is the cheapest place to notice: Close, and describe again.

The card opens Flow Studio by itself after a moment unless you are reading it; press Open flow when ready.

4. Meet the draft in Flow Studio

Flow Studio opens on the Design tab. Click the name in the breadcrumb and rename the draft Plan the weekend (the drafter named it from your words).

You should see:

Read the canvas top to bottom — it is your sentence drawn:

NodeKindWhat it means
On scheduleTriggerWhen the Flow starts. 0 8 * * 1 is a cron expression — we will fix it in step 7.
Until goal completeGoal loop (container)Repeats what is inside until the Goal is met or a limit is hit. The header shows the Goal in short: budget_fit ≥ 0.9 · max 10 · 60m.
Work towards the goalAgentEach pass, the Project's General agent works on the plan and reports metrics — here budget_fit.
Goal evaluatorEvaluatordeterministic — judges the loop; never the model. Compares the metrics with the criteria.
Review resultsApprovalA NexTasks item for the Project owner. The Flow waits.
DoneEndEvery run ends here — approved or rejected, the run is recorded.

Three arrows leave the loop — Goal met · Limits reached · No progress — and all three go to the review. That is deliberate: however the loop ends, a person looks before anything acts on the result.

Around the canvas: the pills Draft · CONFIDENTIAL (the Project's classification, inherited), Saved (autosave — there is no Save button), Test, Run ▾, Publish; the toolbar with the Goal chip budget_fit ≥ 0.9 · 10× · 60m, ✓ Valid and v1; a rail of node kinds on the left to add steps by hand; and at the bottom the box e.g. add a Spin notification after approval — you can keep describing changes in words, and Nexi drafts them as a new version.

5. Open the loop and the Goal

Click the header of the Goal loop container.

You should see:

The Inspector docks on the right. A loop is a small thing with a big description: Label, Description (Loop Container: work → evaluate. Every exit leads to review.), then the Objective — your sentence, which is what the agent reads each pass — the Success criteria budget_fit ≥ 0.9, and the Guardrails Max iterations 10 · Max duration 60 minutes · Token budget.

Now click the Goal chip in the toolbar.

You should see:

The same Goal from the other side, complete. Read the sentence under the guardrails: The engine, not the model, decides when the goal is met and stops at the limits. This is the rule that makes loops safe to publish: an agent can be optimistic, tired or wrong about its own work; the evaluator only compares numbers, and the engine counts passes and minutes. Below it, No progress: No-progress iterations before acting: 3 · Then: ask a person. If three passes in a row change nothing, the loop stops and hands over instead of spending the budget.

6. Tighten a limit — and see autosave

In the Goal Inspector change Max iterations from 10 to 6.

You should see:

The chip now reads budget_fit ≥ 0.9 · 6× · 60m, the loop header max 6 · 60m, and the header says Saved. Nothing else happened: still v1, still a draft. Every edit in the Studio is saved this way; versions are cut only when you publish.

7. Fix what the drafter guessed

Click the Trigger node.

You should see:

Trigger kind: On schedule, Cron (five fields) 0 8 * * 1, and — so you never have to read cron — the plain reading Every Monday at 08:00, the Time zone and the Next fire. Monday is wrong: you said Thursday. The drafter recognised every week and picked a default; this is exactly the kind of thing a plan review is for. Under Arm state: disarmed · A draft is disarmed — publish to arm it — a draft never fires.

Replace the cron with 0 18 * * 4.

You should see:

Every Thursday at 18:00, next fire on the coming Thursday. The fields are minute hour day month weekday; 4 is Thursday. Autosave again.

Click the Review results node too.

You should see:

The approval's settings: Approver Project owner; the Title the owner will see in NexTasks — Agentic result for {{workflow.name}} — review before publishing, a template filled at run time; On timeout: Fail the run after 259200 seconds (three days). The line to remember: The approval is a NexTasks item; the flow waits until it is decided.

8. The same Flow as a list; the Flow's own settings

Press the list icon at the right end of the toolbar.

You should see:

Every step in order, with the validation result for this version. The same six nodes as text, with the arrows written out — → review (complete), review (exhausted), review (needs_human) — and the agent and evaluator nested inside the loop. Prefer this view for reading and for screen readers; the canvas for shaping. Press the icon again to go back.

Press the settings icon next to it.

You should see:

The Flow's own Inspector: Name, Description; Configuration — Trigger · Steps 4 · External writes 0 · approval required; Guardrails — Runs as the person who starts it (the Flow acts with the rights of its initiator, never more), Max run duration 168 h, Governance Not reviewed. External writes 0 is worth a second look: this Flow changes nothing outside Nexi yet — the calendar entry is for a later version, when you add a tool step and policy will require the approval before it.

9. Test it — nothing leaves the platform

Open Run ▾ once, just to read it.

You should see:

On a draft, Run flow is grey and Run with test data is available. A draft cannot run for real; it can always be tested.

Press Test (or Run with test data).

You should see:

Test with data for Plan the weekend · v1: Notifications, external writes and approvals are simulated and marked as such — nothing leaves the platform. The form is the Flow's declared inputs — here only project_id, the owning Project, already filled. Press Start test.

You should see:

The dialog gives way to a run bar above the canvas — Completed · Test · Pass 3 / 6 · frun_… · v1 — and the canvas becomes the run's trace: every node with a green tick and its duration, the loop header pass 3 / 6, and the approval marked simulated. Nobody was asked; nothing was written. That is what a test is.

But look closer: Pass 3 of 6, and the Goal was not met. Press Details.

10. Read what the loop did

The Runs tab opens on this run.

You should see:

Left, the run list — one row, Completed · Test. Right, the run: the Goal with its objective and four numbers — Iterations 3 / 6 · Score 0.00 · Criteria met 0 / 1 · Loop: No progress — handed to a person — then the Budget actually spent (tokens, model calls, cost units) and every pass with its verdict: budget_fit gte 0.9 · actual: —.

This is the most instructive screen of the chapter. The agent worked three times but never reported a budget_fit number, so the evaluator had nothing to compare — three flat passes, and the No progress rule stopped the loop after three, as configured, and took the No progress exit to the review. The engine did exactly what the Goal said; the sentence the agent works from must ask it, in so many words, to return budget_fit as a number between 0 and 1. Edit the Objective in the Goal Inspector to say so, test again, and watch the score move. (In the review fixture that draws these screenshots, the agent is a stand-in that reports no metrics, so the loop always ends this way — the honest behaviour of a Goal whose metric is missing.)

11. Publish

Back on Design, press Publish.

You should see:

The pill turns Published; the modify box at the bottom is gone and a note on the left edge explains why: Published versions are immutable — use "Ask Nexi to modify" to draft the next one. The trigger is now armed — from this moment the Flow will start by itself every Thursday at 18:00, as the person who published it. Publishing is the moment a Flow becomes real; only a Project owner can do it.

Open the v1 ▾ chip.

You should see:

Versions — v1 · Published · date · who. Every publish adds a line here; a run always names the version it ran, and a later version never changes a run that already started.

12. Run it for real and watch it wait

Open Run ▾ again.

You should see:

Now Run flow is available too. Choose it.

You should see:

Run flow — A real run of the published version: agents, tools and notifications act for real; approvals wait for a person. The same input, and one more line: Pins v1. Later versions do not affect this run. Press Run.

You should see:

The run bar reads Waiting · Pass 3 / 6 · … · Waiting for approval: Review results, with Cancel run and Details. The loop ran its passes as before; then the Flow reached Review results and stopped — an amber dot, Waiting for approval. Done has not run. A NexTasks item titled Agentic result for Plan the weekend — review before publishing now exists for the Project owner, with three days to decide — you meet it, as a card on this run, in the next chapter. Approve, and the run completes; reject, and it completes by the Rejected arrow; do nothing, and after three days the run fails, as the approval's On timeout says. This is the difference between a test and a run in one picture.

13. Back on the list

Press Flows in the breadcrumb.

You should see:

Plan the weekend · On schedule · 4 steps · v1 · Goal loop · Published. The Project has its first Flow.

Check

  • Under Flows the row reads Plan the weekend … v1 · Goal loop · Published.
  • In the Studio the trigger says Every Thursday at 18:00 and the Goal chip budget_fit ≥ 0.9 · 6× · 60m.
  • The Runs tab shows two runs: a Test that Completed with the approval simulated, and a real run Waiting for approval: Review results.
  • Run flow was grey while the Flow was a draft and became available after Publish.

What happens underneath

Your sentence went to the Create Flow Skill, which produced a WorkflowSpec — nodes, edges, a GoalSpec — and the plan you read; the draft was saved as v1 before you saw it. Every edit autosaved into the same draft version. Test with data started a run in test mode: the Flow Engine executed the same nodes, but marked the approval and any notification or external write as simulated instead of performing them. The loop is a Flow node with a GoalSpec; each pass the engine ran the agent step, read the metrics at the path the evaluator declares, compared them with the criteria and counted — passes, minutes, flat passes — and it, not the agent, chose the exit. Publish validated the spec, cut an immutable version and armed the schedule trigger. Run flow started a run pinned to that version as you; at the approval node the engine opened a NexTasks item for the Project owner and parked the run; a decision resumes it, a timeout fails it. Every node of every run is a row you can read in the Runs tab and in NexCore's Executions.

If something looks different

What you seeWhyWhat to do
The plan has no loop — just an agent step and an approval.The drafter did not find a goal cue. It looks for “until”, “keep improving”, “iterate”, “goal”.Describe again with “keep improving … until <metric> >= <number>”, or add a Goal from the toolbar chip on the draft.
The Goal chip says quality_score ≥ 0.8 instead of my metric.The criterion was not written as metric · comparison · number, so a default was used and a question added to the checklist.Open the Goal Inspector and edit the criterion; or write “budget_fit >= 0.9” literally next time.
The trigger is “Started manually” or “New case in the Project”.No schedule words (“every week”, “daily”, “every morning”) or event words (“when … arrives”) were found.Change Trigger kind in the Trigger Inspector — the whole Flow stays as it is.
Every pass shows “actual: —” and the loop ends with “No progress”.The agent step did not return the metric the Goal measures, so the evaluator had nothing to compare.Make the Objective ask for the metric by name and type (“return budget_fit as a number 0–1”); check the agent’s output schema on the agent node.
Publish is missing or grey.You are not a Project owner; or the draft is unsaved; or validation found a blocker (the ✓ Valid chip lists it); or NexCore blocked the Flow.Read the toolbar chips — the reason is one of them. A governance block names who to ask.
A real run says Waiting for approval but the owner sees nothing in NexTasks.The approval item could not be created; the run stays parked and nothing has changed.Tell an administrator; the run’s Reference in the Runs tab points to the record. Cancel run is always available to the owner.
I edited the Flow after publishing and the running run did not change.Runs pin the version they started with; edits produce a new draft version.Nothing to fix — publish the new version, and the next run uses it.

Give the agent Tools

Let the Trip planner search the Project and create a task — learn what a tool binding is, read a tool's Posture, see why side effects are refused in a test, and watch a real side effect wait for a person's approval. About twenty minutes.

Decide the approval and read the run

A Flow has parked on “Review results”. Find it, read what it is asking and who may answer, approve or reject with a note for the audit trail, follow both endings, start the same Flow from a chat, and read the History. About fifteen minutes.
